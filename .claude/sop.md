# 项目开发 SOP（AI 协作生命周期规范）

> 每次启动新项目时，请首先读取本文件，并严格按照以下阶段顺序推进。

---

## 全局行为守则（Karpathy Guardrails）

> 以下守则适用于本 SOP 的**所有阶段和所有任务**，不得因任何理由绕过。

### 1. 先思考，再动手
不要假设。不要隐藏困惑。把权衡摆出来。
- 开始前明确陈述你的假设；不确定就问。
- 存在多种理解时，把所有解读列出来，不要自己悄悄选一个。
- 有更简单的方案时说出来，适时推回。
- 有任何不清楚的地方，停下来，说明困惑所在，然后问。

### 2. 简洁优先
最少的代码解决问题，不做任何投机性扩展。
- 不实现没被要求的功能。
- 不为只用一次的代码写抽象。
- 不添加没被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景写错误处理。
- 写了 200 行但 50 行够用？重写。

自问：**"资深工程师会觉得这太复杂了吗？"** 如果是，简化。

### 3. 外科手术式修改
只动必须动的，只清理自己制造的烂摊子。
- 不"顺手优化"相邻的代码、注释或格式。
- 不重构没有问题的东西。
- 匹配已有代码风格，即使你会换一种写法。
- 发现无关的死代码，提一句——但不要删。
- 你的修改产生的孤儿（无用 import/变量/函数）必须清理；原本就有的死代码不删，除非被明确要求。

判断标准：**每一行改动都应该能直接追溯到用户的请求。**

### 4. 目标驱动执行
定义可验证的成功标准，循环直到验证通过。
- "加个校验" → "为非法输入写测试，然后让它们通过"
- "修这个 bug" → "写一个能复现它的测试，然后让它通过"
- "重构 X" → "确保重构前后测试都通过"

多步骤任务必须先陈述计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
```

## 阶段一：需求定义（Proposal Definition）
* **目的**：在动一行代码之前，先把"做什么"彻底讲清楚。

> **📝 阶段一提示词模板（需求定义）**

```
【目标】
帮我完成项目的需求定义阶段。

【步骤与要求】
1. 请以主动提问的方式，逐一向我确认项目的核心需求，包括但不限于：
   - 项目的目标用户是谁？
   - 核心功能有哪些？（MVP 范围）
   - 有哪些明确的非功能性需求（性能、安全、兼容性）？
   - 有哪些已知的限制或边界条件？
2. 每次只问一个问题，等待我回答后再问下一个。
3. 待所有问题确认完毕后，将结论整理成结构化的需求文档，保存至 docs/proposal.md。
```

## 阶段二：系统架构设计（Architecture Design）
* **目的**：在写代码之前，先把"怎么做"的蓝图画好。

> **📝 阶段二提示词模板（架构设计）**

```
【目标】
依据现有的需求文档，为我的项目进行详细的系统架构设计。

【输入】
本地 `docs/proposal.md` 文件。

【输出】
在 docs/ 文件夹下生成详细设计文档 `architecture.md`。

【步骤与要求】
1. 根据需求，将系统划分成具体的独立模块（例如：加载模块、核心逻辑模块、渲染模块等）。
2. 必须保持模块之间的独立性（高内聚、低耦合），以便于后续能分配给不同的独立 Agent 进行开发和单测。
3. 请使用主动提问的方式，针对核心架构设计（如数据流向、状态管理）向我确认，不要盲目自行决定。
```

## 阶段三：任务拆解与进度追踪（Task Breakdown）
* **目的**：把大象装进冰箱，将设计化整为零。

> **📝 阶段三提示词模板（任务拆解）**

```
【目标】
依据详细设计文档，将整个项目拆解为独立、具体的开发任务清单。

【输入】
本地 `docs/architecture.md` 文件。

【输出】
在 docs/ 文件夹下生成整体进度追踪文件 `progress.md`。

【步骤与要求】
1. 为每一个架构中的模块生成单独的、可量化的任务清单。
2. 使用标准 Markdown 的 `[ ]` Checklist 语法来表示任务是否完成。
3. 确保任务颗粒度足够小，以便子 Agent 可以无依赖、闭环地完成单个任务。这一步直接生成，不需要向我提问。
```

## 阶段四：分布式动态编码（Distributed Coding & Verification）
* **目的**：主 Agent 总控看板，生成子 Agent 独立攻坚，单点爆破。

> **📝 阶段四提示词模板（构建 Master 运行总控指南）**

```
【目标】
根据当前项目的所有文档，为自动化 AI 编码代理（如 Claude Code 命令行模式）编写一份最终的、极其详尽的运行总控提示词文件（Master Prompt）。

【输入】
本地 `docs/` 下的 `proposal.md`, `architecture.md`, `progress.md`。

【输出】
在 docs/ 文件夹下生成最终执行提示词 `prompt.md`。

【步骤与要求】
请在生成的 `prompt.md` 中，以绝对严谨的口吻定义以下主/从 Agent 的行为规范：
1. **主 Agent 职责**：负责读取 `progress.md`，总控全局进度。严禁一次性把所有代码任务塞给同一个上下文！
2. **子 Agent 派生机制**：主 Agent 必须针对 `progress.md` 中的每一个独立模块单独派生/分化出一个子 Agent 聊天线去实现代码。
3. **严苛的门禁条件**：子 Agent 每写完一个文件/模块，必须做到：
   - 自动生成对应的单测文件。
   - 必须在终端运行并强行通过类型检查、代码 Lint 以及单元测试。
   - 只有当终端完全无错、测试 100% 通过时，主 Agent 才能更新 `progress.md` 的勾选状态，并开启下一个模块的编写。
4. 生成完毕后将内容保存至 `docs/prompt.md`。
```

## 核心心法

每次你打算让 Claude 做大任务前，对它念一句话：**"我们现在采用本地文档驱动的分布式 Agent 模式开发，请严格配合我完成前期的设计和任务拆解。"**

### 三大优势
1. **防止 AI 记忆衰退**：每个模块都在全新的干净上下文中开发，彻底断绝"改了这里、坏了那里"的连锁 Bug。
2. **极高的工程质量**：子 Agent 被单测、Lint 严密卡死，生成的代码永远有 100% 覆盖率的单测作为安全网。
3. **极度省 Token**：没有臃肿的长对话上下文，每次对话精准高效。
